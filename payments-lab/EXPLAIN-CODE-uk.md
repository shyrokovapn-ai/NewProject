# Як пояснити проєкт на захисті

## Потік даних

`producer.py` читає один денний JSONL-файл, перевіряє обов'язкові поля й часові мітки, сортує події за `receivedAt` і надсилає їх у Redpanda. Ключ Kafka — `invoiceId`: тому всі зміни одного платежу потрапляють до тієї самої партиції. Швидкість задається як платежі за секунду, а затримка між окремими webhook-подіями обчислюється з кількості рядків. Підтвердження доставки перевіряються для кожного повідомлення.

Параметр `--failure-rate 0.30` детерміновано обирає рівно 30% invoice ID (округлено до найближчого цілого; seed за замовчуванням — 7) і змінює їхні кінцеві статуси на `failure` лише під час надсилання. Початковий файл не змінюється. Частка невдалих подій у вікнах може бути більшою за 30%, бо в початкових даних уже є природні відмови.

`consumer.py` працює як учасник Kafka consumer group і читає з призначених йому партицій. Він рахує SHA-256 від канонічного JSON, щоб прибрати точні повторні webhook-и, але залишити наступні зміни статусу того самого платежу. Події групуються за хвилиною `modifiedDate` — це час події. `receivedAt` показує час надходження й визначає порядок відтворення.

Споживач додає до вікна тільки кінцеві статуси `success` і `failure`. Вікно закривається після завершення хвилини й grace period. Загальний watermark дорівнює найменшому event-time прогресу серед призначених партицій, щоб швидка партиція не закрила вікно перед повільною. Подію для вже закритого вікна споживач рахує як `LATE_REJECTED`. Для failure share понад 10% друкується `ALERT`.

Стан дедуплікації та вікон зберігається в пам'яті процесу: перезапуск очищає цей стан. Kafka зберігає самі повідомлення й offset-и групи, тому споживач може продовжити читання; у справжньому production стан агрегатів також треба було б зберігати або відновлювати.

## Пакетний аналіз

`athena.sql` створює зовнішню таблицю над JSON у S3 і додає `dt` як partition. Спочатку `DISTINCT` прибирає точні копії повного webhook-запису. Потім `row_number()` залишає найновішу подію кожного `invoiceId`. Так ми прибираємо повторну доставку, не стираючи реальні переходи `created → processing → success/failure`.

Представлення `payments` приводить рядкові числові поля до типів для розрахунків. Оборот рахується тільки для `success`, а сума з копійок/центів ділиться на 100. Failure rate групується за методом оплати й пристроєм. Година платежу береться з `createdDate`. Запізнення рахується по всіх сирих подіях як різниця між `receivedAt` та `modifiedDate`; таблиця latest-per-invoice для цього не підходить, бо вона вже відкинула старі події. CTAS записує останню подію кожного платежу в Parquet із розбиттям за `dt`.

Glue Crawler окремо виводить типи зі зразків даних. У цьому наборі він зробив числові поля цілими числами, дати — рядками, а `dt` розпізнав як рядкову партицію. Ручна схема краща, коли потрібні контрольовані типи; crawler зручний для швидкого дослідження, але його висновки треба перевіряти.

## Хмарний варіант

`cloud-template.yaml` описує Kinesis Data Stream, Firehose з Kinesis у S3, SNS topic і Lambda trigger від Kinesis. Firehose дописує роздільник рядка, щоб JSON-записи у S3 можна було читати як JSONL. `cloud_producer.py` читає JSONL та передає події в Kinesis із `invoiceId` як partition key. `alert_handler.py` декодує Kinesis batch, знаходить `failure` і надсилає одне коротке SNS-повідомлення на batch.

У цьому AWS акаунті Kinesis API повернув `SubscriptionRequiredException`. Тому шаблон і код підготовлені, але Kinesis/Firehose не розгорнуті, Athena-запит по `stream/raw/` і його скриншот не отримані. Для повного Part 4 треба активувати доступ до Kinesis в акаунті, розгорнути SAM stack, надіслати події, дочекатися буферизації Firehose, виконати Athena-запит і зберегти скриншот та фактичну вартість. Після цього видалити Kinesis і Firehose stack.

## Короткі відповіді на питання викладача

- **Чому event time?** `modifiedDate` показує, коли змінився платіж; `receivedAt` може запізнюватися. Grace period дає пізнім подіям час потрапити у правильне хвилинне вікно.
- **Що робить нульовий grace?** Вікно закривається одразу після завершення хвилини, тому більше подій, що прийшли пізно, відкидаються; лічильники вікон можуть зменшитися.
- **Навіщо Parquet?** Колонковий формат зменшує обсяг читання, коли запит використовує лише частину стовпців. У виміряних трьох запитах сумарне сканування скоротилося приблизно у 405 разів.
- **Чим Kinesis відрізняється від Redpanda тут?** Redpanda працює локально й потребує керування брокером та споживачами. Kinesis/Firehose/S3/SNS — керовані сервіси з окремими тарифами й налаштуваннями доступу.
- **Що обов'язково доробити?** Part 4 потребує фактичного AWS запуску та скриншота Athena; решта вимірювань і код у пакеті.
